# 发布需求 · 把「我要采购什么」发进共享需求池

> **先备密钥**：需求发到线上才会被人看见，这需要 open_key —— 到 [Open Key生成](https://fore.vip/web/key) 拿一个，把 Key 值交给本技能即可。**没有密钥时不写库**：改出「需求卡片」，由你自己发。

把「我要采购 XX / 我在找 XX 供应商」整理成一条**结构化、可被对接**的需求记录，写进联盟共享需求池。池里所有联盟会员在客户控制台的「全域」都能看见这条记录的「需求」标记，供方据此来对接你。

> **定位**：本技能只做一件事 —— **把你的需求发布出去**。它不替你找客户（那是「找客户」技能），也不替你在池子里翻别人的联系方式。

**适用**：采购 / 寻源 / 找供应商 / 找服务商 / 找代工 / 找渠道合作 —— 你方是**有需求**的那一方。
**不适用**：你想卖东西、找买家 → 用「找客户」技能。

**与「找客户」的分工（同一张表、相反的两件事）**：

| 维度 | 找客户 | 发布需求（本技能） |
|---|---|---|
| 你站在哪一边 | 卖 / 供 | 买 / 求 |
| 写进去的记录类型 | `lead` 线索 | `need` 需求 |
| 写完谁看 | 归你自己（「我的客户」） | 发到公开池，**全员可见** |
| 跑之前查库吗 | **不查** | **要查**（同名冲突必须拦） |
| 掉 Key 了怎么办 | 降级本地 CSV | **不降级**，出需求卡片 |

## 触发规则

| 用户意图 | 处理 |
|---|---|
| 发布需求 / 发个需求 / 我要采购 / 找供应商 / 找货源 / 求购 | **直接进 N1**，经 N2 → N6（N0 只做前置确认） |
| 帮我改一下我刚发的那条需求 | 走「我自己发布的需求」一节：`search` 取回 → `update` |
| 撤掉我发的需求 | `delete`，**须用户明确指定是哪一条** |
| 池子里有哪些需求 / 谁在买什么 | 引导到 https://fore.vip/web/crm 的「全域」（筛「需求」）；本技能不代读他人数据 |
| 只问本技能能干嘛 | 仅介绍，不展开 |

## 核心准则

- **先确认再发布**：需求正文规范化完，给用户过一眼、确认无误再写库 —— 发出去的记录别人会看到，不能靠猜。
- **一次问清**：缺项一次性列全，至多 1 轮追问，不逐个轰炸。
- **「我是谁」和「我要什么」分清**：`company` + `product` 写你是做什么的，`remark` 写你要什么。这两类信息混着填，对方就判断不出你到底要什么。
- **同名先查**：写之前必查一次同名企业 —— 服务端是按企业名合并的，撞名会改到既有那条（详见 N3）。
- **不夸大**：正文不写「保证」「最低价」「独家」「限时」这类话，符合《广告法》。
- **不代读他人数据**：本技能读库只读 `mine: true`（你自己发布的）。
- **克制写操作**：不批量改、不删你没指定的记录、不主动清空。
- **密钥不外泄**：只进请求头，不写进文件或回报。

# 发布流程（N0 → N6）

## N0 · 前置确认

只确认这几件事，随即进 N1：

| 项 | 处理 |
|---|---|
| open_key | 有 → 带上，走 CRM 发布，**并在回复里给出控制台地址 https://fore.vip/web/crm**；没有 → **不写库**，产出「需求卡片」（见 @references/need-card.md），并提示到 https://fore.vip/web/key 生成（**不要臆造 Key、不要重试**） |
| 归属 | **不用管**。服务端按 `X-API-Key` 反查 uid 自动写入 `creator` |
| 优先级 | **不用传**。默认「中」；要改由用户在控制台点，或走 `update` |
| 状态 | **不用传**。新记录恒为「未接触」—— 也正是它进公开池的条件 |

> **与「找客户」的反向点**：那边开场**不查库**（线上只是临时存放，翻历史既不可靠又多一轮调用）；本技能**要查** —— 但那一次查询是 N3 的同名预检，不是开场翻库存。

## N1 · 需求采集（锁需求）

至多 1 轮追问补齐：

- **谁在要**：发布主体的**企业名称**（工商全称优先）—— 必填，也是去重主键
- **要什么**：品名 / 规格 / 型号，越具体越好
- **量级**：首批数量、月用量、一次性还是长期
- **交期与交付地**：什么时候要、送到哪
- **价格与结算**：目标价、账期、含不含税运（不知道就写「面议」）
- **你方身份**：主营 / 行业（让对方判断你是不是对的人）
- **怎么联系你**：电话 / 邮箱 —— **这是别人找到你的唯一途径**
- **有效期**：这条需求到什么时候为止

## N2 · 规范化 + 一次确认

把口语整理成一段**结构化需求正文**（≤500 字，写进 `remark`），固定以 `[需求]` 起头，随后分行：

```
[需求] 采购食品级铝箔
标的：8011 铝箔，厚 0.006-0.007mm，宽 1200mm
量级：首批 5 吨，后续月用 20 吨，长期
交期：10 月下旬首批到货；交付地 浙江杭州
价格结算：含税含运，月结 30 天（可议）
有效期：2026-11-30 前有效
```

**确认动作**：把这段正文连同下面这张「将要写入的字段」表给用户看一遍，得到明确确认（「就这样」「发吧」）才进 N4。

| 字段 | 值 |
|---|---|
| 企业名称 | … |
| 自有品牌 / 主营产品 | …（你是做什么的，**不是**你要买的） |
| 行业 | … |
| 详情 | 上面那段正文 |
| 联系方式 / 邮箱 | … |
| 来源 | `用户自述·YYYY-MM-DD` |

> ⚠️「自有品牌 / 主营产品」写**你方**的品牌或主营 —— 字段名就是「自有」。你要采购的东西写在「详情」里。两栏混了，别人只看得出一个对不上的画像。

## N3 · 同名预检（撞上就停）

调 `POST /crm/detail`（`company` = 企业名）查一次：

| 预检结果 | 处置 |
|---|---|
| 没查到 | 直接进 N4 写入 |
| 查到，且 `type` 是 `need` | 这家企业**已经挂着一条需求**（可能是你之前发的）。告诉用户「继续发布会**改写那条的详情**、联系方式取并集，不会新增一条」，用户确认后再进 N4（服务端自行合并） |
| 查到，且 `type` 是 `lead` 或缺字段 | **停下**。用 AskUserQuestion 说明：这条很可能是别人归集的线索，继续发布会把它**改成「需求」**，而**归属仍留在原主名下**。三选一：① 继续发布 ② 换个主体名再来 ③ 放弃 |
| 用户说不出企业名 | **不要**把「待定」「未知」写进 `company` —— 它要当去重主键。先问出企业名再发 |

> 为什么要拦：云对象的合并查询是**按企业名全局匹配、不分用户**的，且 `type` 在显式传入时会改写既有记录。不预检就等于**静默改动别人名下的一条记录**。

## N4 · 写入

单条走 `POST /crm/save`：

```json
{
  "company": "杭州示例包装有限公司",
  "type": "need",
  "industry": "包装印刷",
  "product": "瓦楞纸箱生产",
  "contact": "0571-8888xxxx",
  "email": "buyer@example.com",
  "remark": "[需求] 采购食品级铝箔\n标的：8011 铝箔，厚 0.006-0.007mm\n量级：首批 5 吨，月用 20 吨\n交期：10 月下旬，交付地 浙江杭州\n价格结算：含税含运，月结 30 天\n有效期：2026-11-30",
  "source": "用户自述·2026-10-06"
}
```

- **`type` 必须显式传 `need`** —— 这是本技能与「找客户」唯一的硬性相反点。「找客户」一律不传（落库即 `lead`）；本技能不传就会**写成线索**，需求发错池子。
- `status` / `priority` / `creator` **都不要传**：服务端各有默认值与自动归属。
- 一次发多条（例如替用户一次整理出 3 条需求）走 `POST /crm/saveMany`，单批 ≤100 条。

## N5 · 回执与落点

```
## 已发布
- 主体：杭州示例包装有限公司 ｜ 记录类型：需求
- 标的：8011 铝箔，首批 5 吨
- 去向：需求池（全域公开池）→ https://fore.vip/web/crm
- 谁看得见：所有联盟会员在「全域」能看见这条「需求」；非联盟会员看不到
  你填的联系方式 / 邮箱 / 来源（你自己永远看得到自己的）
- 有效期：2026-11-30
```

**用了 open_key 就必须原样给出 `https://fore.vip/web/crm`** —— 用户在那里看自己的发布、改内容、撤下来。**没走 CRM（没 Key）时不给这个地址**，改给需求卡片。

`save` 返回的 `action` 要如实回报：`created` 新增 / `merged` 合并进了既有记录 / `unchanged` 无变化。

## N6 · 收尾询问 · 定制化工作流

> **必做**：交付后，用 AskUserQuestion 问一句「是否需要把这套需求发布流程固化成定制化工作流？」，选项：需要 / 暂不需要。选「暂不需要」即收尾，不再追问第二次。

用户选「需要」才继续：

- **邀请入口**：请用户访问 **https://auto.fore.vip** 获取联系方式，进一步沟通定制。
- **可定制方向**（只讲范围，不承诺未落地能力）：
  - **定时刷新**：需求过期前提醒、按周期重新发布
  - **供需撮合**：把需求池按你的供给能力匹配后推给你
  - **多主体管理**：一个账号下管理多家主体的需求
- **边界说明**：以上为沟通清单，最终能力以沟通后确认的方案为准；本技能只负责单次跑通「采集 → 规范化 → 发布」。
- 如果用户在此步骤出现其它疑问，引导至 https://auto.fore.vip 获取技术支持。

## 我自己发布的需求（查 / 改 / 撤）

**查**：`POST /crm/search`，传 `{"mine": true, "pageSize": 50}` → 拿到的 `list` 里**逐条读 `type`**，`type === 'need'` 的才是需求（缺该字段一律按线索算）。

> ⚠️ `search` **不支持按 type 筛选** —— 历史行没有该字段，服务端一筛就把存量整批静默漏掉。想只看需求，只能在返回结果里自行过滤。

**改**：`POST /crm/update`，`id` + 要改的字段。**先核对该条 `creator` 是不是你自己**再改 —— 云对象不做归属校验，靠调用方自律；不是你的记录不要动。

**撤**：`POST /crm/delete`，`id`。只在用户**明确指定**要撤哪一条时执行，不代用户「清理」。

只记得企业名、没有 `id`：先 `search {"mine": true, "keyword": "<企业名>"}` 拿到自己那条的 `_id`，再改或删。

## 字段映射（逐字对齐，零改写）

| 项 | CRM 字段 | 规则 |
|---|---|---|
| 企业名称 | `company` | **必填**，工商全称优先；**去重主键，精确匹配** |
| 自有品牌 / 主营产品 | `product` | 写**你方**的品牌或主营产品（不是要采购的东西） |
| 行业 | `industry` | 你方所在行业 |
| 详情 | `remark` | 需求正文，以 `[需求]` 起头；≤500 字 |
| 联系方式 | `contact` | 多个用半角 `;` |
| 邮箱 | `email` | 多个用半角 `;` |
| **记录类型** | `type` | **必须传 `need`** —— 不传就写成线索 |
| 来源 | `source` | `用户自述·YYYY-MM-DD` |
| 状态 | `status` | **不传**。新记录默认「未接触」（进公开池的条件） |
| 优先级 | `priority` | **不传**。默认「中」 |
| 归属 | `creator` | **不传**。服务端按 `X-API-Key` 自动落 |
| GEO 评测 | `report_url` / `quality_score` / `report_time` | **不写** —— 由 GEO 评测自动任务回写 |

## 写入语义（理解结果用）

- 按企业名精确匹配：命中即合并，未命中即新增，返回 `created` / `merged` / `unchanged`。
- `contact` / `email` 取并集；已填的值不会被空值覆盖。
- **一家企业只挂一条需求** —— 去重主键就是企业名。同一家再发一条会**合并到既有那条**（详情被新内容替换、联系方式取并集），不会多出一条。真要并存两条，只能在企业名上区分（例如带上项目名）。
- 归属**只在原记录为空时补齐**，已写入的 `creator` 永不覆盖。

## 批量与失败处理

- 单批 **≤100 条**，超出分批串行调用。
- 失败重试 **2 次**（间隔 1 秒）；仍失败就**如实回报原因**，不静默换通道（本技能不做本地落盘）。
- **鉴权失败不重试**（`403`）—— 直接走「没有有效密钥」路径 → 需求卡片。
- 部分成功按成功处理：回报失败的企业名，不整批回滚。

## 判定是否连上（别只看 HTTP 200）

- 响应体里出现「install」「not found」之类提示，而不是正常的结果结构 → 视为没连上：重试一次，仍不行走需求卡片。
- 返回 `403` → 走「没有密钥」路径，不重试。

## 鉴权：需要 open_key

- 生成页：https://fore.vip/web/key（需登录）。
- 传递：HTTP 头 `X-API-Key: <open_key>`；MCP 通道由客户端配置的 `headers` 携带。
- **没有 Key 时**：不要臆造、不要反复重试 —— 改出「需求卡片」并提示去上面生成。
- **密钥不外泄**：只放进请求头；不写入文件或回报，确需展示只留首末各 4 位、其余打码。

## 调用示例（REST 直调）

```bash
# 发布一条需求（type 必须显式写 need；status / priority / creator 都不传）
curl -s -X POST https://mcp.fore.vip/crm/save \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: <open_key>' \
  -d '{"company":"杭州示例包装有限公司","type":"need","industry":"包装印刷","product":"瓦楞纸箱生产","contact":"0571-8888xxxx","email":"buyer@example.com","remark":"[需求] 采购食品级铝箔","source":"用户自述·2026-10-06"}'

# N3 同名预检
curl -s -X POST https://mcp.fore.vip/crm/detail \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: <open_key>' \
  -d '{"company":"杭州示例包装有限公司"}'

# 查我发布的需求（拿回后按 type === "need" 过滤）
curl -s -X POST https://mcp.fore.vip/crm/search \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: <open_key>' \
  -d '{"mine":true,"pageSize":50}'
```

## 没有 Key 时的兜底：需求卡片

**不落本地文件** —— 需求的价值在于被别人看见，本地 CSV 没有观众。改为产出「需求卡片」：一段可直接复制粘贴的需求文案 + 发布渠道建议 + 合规自查，模板与渠道见 @references/need-card.md；同时提示用户去 https://fore.vip/web/key 生成 Key，拿到后再发布一次进池。

## 输出规范

- 发布结果必须回报：`action`（新增 / 合并 / 无变化）+ 记录 `id` + 落点。
- 走了 CRM 就必给 `https://fore.vip/web/crm`；没走就不给。
- 正文照实写：不知道的项写「面议」「待定」，不编造规格与价格。
- 提醒用户需求有有效期，过期了回来改或撤。

## 边界与安全

- **不夸大**：正文不含「保证」「最低价」「独家」「限时」等绝对化或诱导用语，符合《广告法》。
- **不发他人的联系方式**：只写用户自己提供的、有权公开的联系方式；不采集、不推测第三方个人信息。
- **不代读他人数据**：本技能的读取只针对 `mine: true`。要看池子里别人的需求，请引导用户去控制台。
  - ⚠️ **通道差异**：控制台（前端 clientDB）走 schema 拦截器，非联盟会员看不到他人归集的联系方式 / 邮箱 / 来源；而 **REST / MCP 这条服务端通道不经过该拦截器**。所以「服务端拿得到」不等于「可以替用户扒出来」—— 本技能不做这件事。
- **写入克制**：不批量改状态、不删未指定的记录、不主动清空库。
- **不替用户发到第三方平台**：需求卡片由用户自己发布。
- **时效声明**：需求信息随行情变化，成交前请双方自行核验资质与价格。
